#2A — Auto-Navigate After Generation

When generation completes, auto-navigate to /content/[id] with a success toast instead of leaving the user on a dead-end preview. Eliminates the "now what?" moment.

Current flow: Generation finishes → user sees static preview + "Open in Library" button → clicks button → arrives at content viewer

Proposed flow: Generation finishes → brief completion beat (0.5s) → auto-morphs to /content/[id] via View Transitions API → user is already in the editor with full toolbar
2

#6 — Skeleton-to-Content Crossfade

Replace the hard swap between GenerationSkeleton and streaming content with a layered crossfade where skeleton bars dissolve as real text appears.

Current: AnimatePresence mode="wait" — skeleton fades out entirely, then content fades in (sequential)

Proposed: Switch to mode="popLayout" or layer both — skeleton fades out (0.2s) while content simultaneously fades in, creating an overlap window where content "emerges through" the skeleton
3

#8 — Form Step Shared-Element Transitions

When the user picks a content type card and advances to Step 2, the selected card should visually compress and travel into a "chosen type" badge in the step header — creating a visual thread.

Current: Steps slide horizontally (x: ±24px) via AnimatePresence mode="wait". Clean but generic — no visual connection between what you picked and where you are.

Proposed: Use Framer Motion layoutId on the selected card so it morphs into a compact badge/chip at the top of Step 2/3. The illustration shrinks, the title stays, color persists. Creates a "you chose this" breadcrumb trail.
4

#9 — Content Viewer Exit Transition

Smooth the "back to library" navigation with a reverse morph — content compresses back into its card position in the grid.

Current: View Transitions API handles card→page morph on entry. But exiting (back button) just does a generic page crossfade — the spatial relationship is lost.

Proposed: Add view-transition-name matching on the content viewer's title/badge/container elements so the browser can reverse-morph them back to the library card position. Already have vtName() utility — just needs matching names on the viewer side elements (partially done in ContentViewerHeader already).
